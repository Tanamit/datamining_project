## 1. What this project does

We build a data warehouse (DW) and a data mining layer to detect fraud in mobile money transactions.

- **Main data:** PaySim, a synthetic mobile money dataset on Kaggle (`ealaxi/paysim1`). It has 6,362,620 transactions. It was generated by a simulator calibrated on real transaction logs.
- **Extra data:** after advisor feedback (section 2), we add linked sources that we generate ourselves, plus a real holiday calendar.
- **Warehouse:** PostgreSQL 16 in Docker. Flow: raw source, staging, warehouse (star schema), OLAP, mining.
- **Mining (planned):** classification with XGBoost, anomaly detection with Isolation Forest, both compared against baselines.

Hypotheses from the proposal:

- H1: fraud is concentrated in specific transaction types.
- H2: transactions that empty the origin account are disproportionately fraud.
- H3: fraud rate changes over time (hour or day).

## 2. Advisor feedback and our decisions

Feedback on the proposal:

1. PaySim alone is too clean, so ETL would have little to do. We need several linked data sources.
2. Generating extra linked data ourselves is acceptable.
3. The 5 complex OLAP queries must come from real user use cases.

Decisions so far:

- Keep PaySim as the core fact source.
- Generate three linked sources: a channel log, a branch master with history, and a holiday calendar. Details in section 7.
- Work locally with Docker Compose (not Google Colab). Reason: the live demo and the OLAP timing benchmark both need a stable environment, and data must persist between sessions.
- PaySim account IDs are random strings made by the simulator, so no outside dataset can be joined to them at account level. This is why extra sources are generated and keyed on a transaction ID.

## 4. Setup (reproduce from scratch)

Requirements: Docker Desktop (engine must be running) and Docker Compose v2.

**4.1 Get the data**

Download `paysim1` from Kaggle (`kaggle.com/datasets/ealaxi/paysim1`), unzip, and place this file in `data/`:

```
data/PS_20174392719_1491204439457_log.csv     (about 470 MB)
```

The header must be:

```
step,type,amount,nameOrig,oldbalanceOrg,newbalanceOrig,nameDest,oldbalanceDest,newbalanceDest,isFraud,isFlaggedFraud
```

**4.2 Create `.env`** (development values only; do not commit)

```
POSTGRES_USER=dw
POSTGRES_PASSWORD=dwpass
POSTGRES_DB=dw
```

**4.3 `docker-compose.yml`**

```yaml
services:
  db:
    image: postgres:16
    container_name: dw_postgres
    env_file: .env
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./data:/data:ro
      - ./sql:/sql:ro
volumes:
  pgdata:
```

Notes:

- The `pgdata` volume keeps the database after `docker compose down`. Without it, data would be lost when the container is removed.
- If port 5432 is taken, change the left side to `"5433:5432"`.

**4.4 Start the database**

```
docker compose up -d
docker compose logs db --tail 3
```

Wait until the log shows `database system is ready to accept connections`.

**4.5 Create the table and load PaySim**

```
docker compose exec db psql -U dw -d dw -f /sql/01_paysim_raw.sql
docker compose exec db psql -U dw -d dw -c "\copy paysim_raw (step,type,amount,nameorig,oldbalanceorg,newbalanceorig,namedest,oldbalancedest,newbalancedest,isfraud,isflaggedfraud) FROM '/data/PS_20174392719_1491204439457_log.csv' CSV HEADER"
docker compose exec db psql -U dw -d dw -c "SELECT COUNT(*) FROM paysim_raw;"
```

The count must be 6362620.

The raw table intentionally has no primary key and no constraints. Its job is to accept the data exactly as it arrives, so that ETL can detect and count the problems instead of the load failing or silently dropping rows.

`sql/01_paysim_raw.sql`:

```sql
DROP TABLE IF EXISTS paysim_raw;

CREATE TABLE paysim_raw (
  txn_id          bigint GENERATED ALWAYS AS IDENTITY,
  step            int,
  type            text,
  amount          numeric(14,2),
  nameorig        text,
  oldbalanceorg   numeric(14,2),
  newbalanceorig  numeric(14,2),
  namedest        text,
  oldbalancedest  numeric(14,2),
  newbalancedest  numeric(14,2),
  isfraud         smallint,
  isflaggedfraud  smallint
);
```

Why `numeric` and not `float`: `numeric` stores exact decimal values, so sums over millions of money amounts do not drift. `txn_id` is a surrogate transaction ID equal to the row number in the CSV (excluding the header). It is needed because `(nameorig, step)` is not unique (section 5.2).

Check after loading: `SELECT txn_id, step, type, amount FROM paysim_raw ORDER BY txn_id LIMIT 3;` should return amounts 9839.64, 1864.28, 181.00.

**4.6 Run the profiling queries**

```
docker compose exec db psql -U dw -d dw -f /sql/02_profile.sql
docker compose exec db psql -U dw -d dw -f /sql/03_profile.sql
docker compose exec db psql -U dw -d dw -f /sql/04_profile.sql
```

## 5. What we found in PaySim

All numbers below come from queries run on the loaded table (`02_profile.sql` and `03_profile.sql`). Results of `04_profile.sql` are pending (section 9).

### 5.1 Size and time range

| Item | Value |
|---|---|
| Rows | 6,362,620 |
| Distinct origin accounts | 6,353,307 |
| Distinct destination accounts | 2,722,362 |
| Steps | 1 to 743 (1 step = 1 hour, about 31 days) |

Almost every origin account appears once. Consequence: a slowly changing dimension (SCD Type 2) on accounts would have nothing to track. We use a branch dimension instead.

### 5.2 Key collision

There are 6,362,573 distinct `(nameorig, step)` pairs, which is 47 fewer than the row count. The rows sharing a key that we inspected are different transactions (different amounts and destinations), for example one customer paying two merchants in the same hour. They are not duplicates and must not be deleted. Joining another table on `(nameorig, step)` would multiply rows, so all linked sources use `txn_id`.

### 5.3 Fraud by transaction type

| Type | Rows | Fraud rows | Fraud rate |
|---|---|---|---|
| TRANSFER | 532,909 | 4,097 | 0.7688% |
| CASH_OUT | 2,237,500 | 4,116 | 0.1840% |
| CASH_IN | 1,399,284 | 0 | 0% |
| DEBIT | 41,432 | 0 | 0% |
| PAYMENT | 2,151,495 | 0 | 0% |

- Total fraud is 8,213 rows (about 0.13% of all rows). All fraud is in TRANSFER and CASH_OUT, which supports H1 by counting (no statistical test yet).
- Type names use an underscore (`CASH_OUT`), not a hyphen as written in the proposal.
- TRANSFER fraud rate is about 4.2 times the CASH_OUT rate, even though the fraud counts are close, because CASH_OUT has about 4.2 times more transactions.
- RQ1 asks for the ratio between the riskiest and safest types. Three types have zero fraud, so that ratio is undefined. We compare TRANSFER with CASH_OUT and state that the other three have no fraud.

### 5.4 The platform's own flag is a weak baseline

| isFlaggedFraud | isFraud | Rows |
|---|---|---|
| 0 | 0 | 6,354,407 |
| 0 | 1 | 8,197 |
| 1 | 1 | 16 |

Only 16 rows are flagged, and all 16 are real fraud (precision 100%). But it catches 16 of 8,213 frauds (recall about 0.19%). This is too weak to be a meaningful baseline. A new baseline will be chosen after the pending queries.

### 5.5 Destination accounts

| Destination prefix | Rows | Both destination balances = 0 | Fraud rows |
|---|---|---|---|
| M (merchant) | 2,151,495 | 2,151,495 (all) | 0 |
| C (customer) | 4,211,125 | 165,787 (about 3.94%) | 8,213 |

- Merchant accounts always have zero destination balances: a structural placeholder, not missing data. Merchants appear only as PAYMENT destinations.
- Customer accounts also show zero destination balances in 165,787 rows. The proposal said only merchants lack balances, which is incomplete. ETL must handle the two cases separately and must not impute them the same way.
- All fraud is in customer-destination rows.

### 5.6 Balance consistency (data is clean in format, not in logic)

Check used: old balance, plus the amount for CASH_IN or minus the amount for other types, should equal the new origin balance (tolerance 0.01).

| Type | Rows | Mismatching rows | Share |
|---|---|---|---|
| CASH_IN | 1,399,284 | 33 | about 0% |
| DEBIT | 41,432 | 11,786 | 28.4% |
| PAYMENT | 2,151,495 | 1,101,124 | 51.2% |
| CASH_OUT | 2,237,500 | 1,981,123 | 88.5% |
| TRANSFER | 532,909 | 507,529 | 95.2% |

Many rows do not follow simple balance arithmetic, so the dataset has real problems for ETL even though it is well-formed. We will not delete these rows (it would remove most of CASH_OUT and TRANSFER). We will add a `balance_consistent` flag in the warehouse and report data quality before and after cleaning. The cause of the mismatches is not yet known.

## 6. Planned warehouse design

Not built yet. Direction:

- **Fact:** `fact_transaction` at one row per transaction, with `txn_id` as a degenerate dimension.
- **Dimensions:** transaction type, time (with holiday and payday flags), channel, and branch.
- **SCD Type 2** on the branch dimension (region and tier change during the month).
- **Staging layer** receives all raw sources before the warehouse.
- Account role (customer or merchant) is derived from the ID prefix.

## 7. Planned additional sources

PaySim stays the core. We add three linked sources. Generator scripts will live in this repo with fixed random seeds so anyone can rerun them.

| Source | Format | Linked by | Planned data problems |
|---|---|---|---|
| Channel log (channel, branch per transaction) | CSV, two files with different column names | `txn_id` | 3% null channel, 5% lowercase channel, 2% duplicate rows, 1% branch IDs missing from the master, schema drift between files |
| Branch master (about 500 branches, with history) | JSON change log | `branch_id` | about 100 branches change region during the month, 2% inconsistent region spelling |
| Holiday and payday calendar | CSV built with the Python `holidays` package (Thailand) | date | none (real holiday data); payday is our own rule (day 25 and month end) |

Rules to keep results honest:

1. Channel and branch are generated independently of `isFraud`. Otherwise a model would only rediscover the pattern we planted.
2. The report states which data we generated and the exact rates of injected problems. These rates are the ground truth used to check how well the ETL cleans data (`dq_ground_truth.json`).
3. Assumption: PaySim has no dates, so step 1 is mapped to 2025-12-01 00:00 and timestamp = start + (step - 1) hours. This is documented as an assumption.

## 8. OLAP use cases (draft, to be validated with real users)

The advisor requires use cases from real users. Plan: interview one or two people in fraud, risk or compliance for about 15 minutes, using three questions (what do you check first each day or week; which question takes hours in Excel today; which report goes to management or the regulator). If no one is available, we label these as proxy personas. Draft queries:

1. Fraud ops: fraud rate by type, channel and hour (ROLLUP/CUBE).
2. Fraud ops: 6-hour moving fraud rate per branch (window function).
3. Compliance: top 10 branches by fraud amount per week, drill-down region to branch, using the branch version valid at transaction time.
4. Compliance: effectiveness of the platform flag versus true fraud, by week and type.
5. Risk: fraud rate on holidays versus normal days and around payday, by type.
